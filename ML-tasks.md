# Задания: ML (ИИ-слой)

Формат каждого задания: ветка, источник истины, границы скоупа,
подпункты, Definition of Done.

**Общий источник истины:** `contracts/llm_contract.md` (HTTP и контракт
модели), `contracts/llm_schema.json` (схема ответа),
`flows.md` «Сценарий 2+4».

**Общий DoD для всех заданий:**

```bash
make ml-test
```

Плюс: `GET /health/model` отвечает корректно, HTTP-контракт из
`llm_contract.md` §2 не нарушен.

**Твоя зона:** `ml_service/` целиком. Ты не пишешь роуты бэкенда, не
трогаешь фронт и DOCX. Граница ровно одна — `POST /api/v1/process`.

**Главное свойство твоей работы:** бэкенд не должен знать, что у тебя
внутри. Ты можешь поменять модель, перейти на теги вместо JSON, уйти в
rule-based — HTTP-контракт при этом остаётся прежним, и тимлид ничего
не заметит.

# ML-01. Гейт: стабильный JSON от локальной модели

**Ветка:** `ml/01-ollama-gate`
**Источник истины:** `contracts/llm_contract.md` §4, `llm_schema.json`
**Блокируется:** ничем
**Приоритет:** P0, **первые три часа, решается судьба подхода**

**Не реализовывать:** промпт целиком, Fact Guard, fallback, эндпоинт.
Только замер: способна ли модель отдавать валидный JSON.

### 1.1. Задача

```bash
docker compose exec ollama ollama pull qwen2.5:7b-instruct
```

Прогнать 20 разных черновиков через модель с `format` из
`llm_schema.json` и посчитать долю ответов, которые парсятся
`json.loads` с первого раза.

### 1.2. Вызов

```python
response = await client.post(f"{OLLAMA_URL}/api/generate", json={
    "model": "qwen2.5:7b-instruct",
    "prompt": prompt,
    "format": json.load(open("llm_schema.json")),
    "stream": False,
    "options": {"temperature": 0.2},
})
```

Температура 0.2. Выше — модель начинает «улучшать» факты, и это прямо
ломает сценарий 4.

### 1.3. Гейт на третьем часу

| Доля валидных JSON | Решение |
|---|---|
| ≥ 90% | идём по плану, repair на всякий случай |
| 70–90% | repair обязателен, план не меняем |
| < 70% | **немедленно писать в чат**, переходим на план Б |

### 1.4. План Б

Модель отвечает не JSON, а размеченным текстом:

```
<TEXT>Прошу предоставить ежегодный оплачиваемый отпуск...</TEXT>
<ADDRESSEE>null</ADDRESSEE>
<AUTHOR>null</AUTHOR>
```

Парсим регулярками. Менее элегантно, надёжнее на 7B.

**HTTP-контракт при этом не меняется.** В этом и был смысл отдельного
сервиса. Не стесняйся плана Б: критерий дословно говорит, что
«сложность подхода сама по себе не даёт преимущества».

### 1.5. Проверки

- модель скачана на сервер заранее, не тянется при старте контейнера
- первый запрос после простоя укладывается в 90 секунд
- `OLLAMA_URL` берётся из переменной окружения, не захардкожен

### 1.6. Тесты

1. 20 прогонов, доля валидных JSON записана в чат команды.
2. Замер медианной латентности на длинном черновике (3000 символов).
3. Ответ содержит все ключи из `requisite_keys`.

### DoD ML-01

Цифра доли валидных JSON опубликована в чате, решение по гейту принято
и объявлено.

# ML-02. Промпт и эндпоинт обработки

**Ветка:** `ml/02-process-endpoint`
**Источник истины:** `contracts/llm_contract.md` §2, §3
**Блокируется:** ML-01
**Приоритет:** P0

**Не реализовывать:** Fact Guard (ML-04), fallback (ML-05).
Пока `fact_guard` возвращается как `{"verdict": "clean", ...}` заглушкой.

### 2.1. Эндпоинт

```
POST /api/v1/process
{
  "draft": "...",
  "doc_type": "memo",
  "doc_type_name": "Служебная записка",
  "structure_hint": "кому -> от кого -> суть -> просьба -> подпись",
  "requisite_keys": ["addressee", "author", "position", "subject", "doc_date"],
  "request_id": "uuid"
}
```

**Ты не читаешь `doc_types/*.yaml`.** Бэкенд присылает всё нужное в
запросе: название типа, подсказку по структуре и список ключей.

Зачем: добавление пятого типа документа должно быть правкой одного YAML
на бэкенде. Если бы `ml_service` тоже читал конфиги типов, они бы
разъехались. Это готовый ответ на защите по критерию «готовность к
развитию».

### 2.2. Промпт

Живёт в `llm/prompts/process.txt`, версионируется в git. Правки промпта
— обычный коммит с понятным сообщением, чтобы на защите можно было
показать историю.

Обязательные блоки по порядку:

1. **Роль** — одна строка
2. **Запрет на выдумывание** — явный перечень: даты, ФИО, должности,
   номера, суммы, названия. Формулировка «если сведения нет — ставь
   null», а не «постарайся не выдумывать»
3. **Тип и структура** — подстановка `doc_type_name` и `structure_hint`
4. **Формат ответа** — скелет JSON, явно «только JSON, без markdown»
5. **Few-shot: два примера**
6. **Исходный текст**

### 2.3. Второй пример обязателен

Один пример — черновик со всеми реквизитами. Второй — **черновик без
адресата**, где в ответе стоит `null`.

Без второго примера модель склонна выдумывать правдоподобного адресата,
и сценарий 3 разваливается целиком. Это 6 баллов.

### 2.4. Гарантии бэкенду

- `requisites` содержит **ровно** ключи из `requisite_keys` — ни больше,
  ни меньше
- отсутствующее значение — `null`, не пустая строка и не пропущенный ключ
- `improved_text` непустой
- лишний ключ от модели — выбросить молча
- пустая строка вместо `null` — нормализовать в `null`

### 2.5. Тесты

1. Ответ содержит ровно ключи из `requisite_keys`.
2. Черновик без адресата → `addressee: null`.
3. Лишний ключ от модели отброшен.
4. Пустая строка нормализована в `null`.
5. Просторечие «задолбался» отсутствует в `improved_text`.
6. Орфографическая ошибка исправлена.
7. `improved_text` пустой → ответ не отдаётся, уход в fallback.

### DoD ML-02

Общий DoD + грязный черновик через curl превращается в деловой текст
с корректным JSON реквизитов.

# ML-03. Извлечение якорей

**Ветка:** `ml/03-anchors`
**Источник истины:** `contracts/llm_contract.md` §5.1
**Блокируется:** ML-02
**Приоритет:** P0 — основа сценария 4

**Не реализовывать:** сверку — это ML-04. Здесь только извлечение.

### 3.1. Пять категорий

Скелет `guard/anchors.py` сгенерирован bootstrap-скриптом с готовыми
регулярками. Твоя задача — проверить их на реальных черновиках и
довести.

| Категория | Что ловит | Примеры |
|---|---|---|
| `date` | даты цифрами и словами | `10.06.2025`, `10 июня 2025` |
| `amount` | числа с единицами | `14 календарных дней`, `50 000 руб.` |
| `fio` | ФИО полностью и с инициалами | `Иванов И.И.`, `Петров Пётр Петрович` |
| `number` | регистрационные номера | `№ 15`, `№ 47/2-К` |
| `org` | названия в кавычках | `«Ромашка»` |

### 3.2. Жадность — главный риск

Если регулярка на `amount` поймает **каждое** число в тексте, Fact Guard
начнёт блокировать нормальные переформулировки, и сценарий 2 сломается
о собственную защиту.

Правило: якорь — это число **с единицей измерения или в явно значимом
контексте**. Голое «3» в середине предложения якорем не является.

### 3.3. Нормализация

```python
def normalize(anchor: str) -> str:
    # нижний регистр, схлопнутые пробелы, убранные точки в инициалах
```

Без неё `Иванов И.И.` и `Иванов И. И.` посчитаются разными, и Guard
выдаст ложное срабатывание на пустом месте.

### 3.4. Тесты

1. `10.06.2025` и `10 июня 2025 года` оба попадают в `date`.
2. `14 календарных дней` попадает в `amount`.
3. Голое число `3` в тексте **не** попадает в `amount`.
4. `Иванов И.И.` и `Иванов И. И.` нормализуются одинаково.
5. `№ 47/2-К` попадает в `number` целиком.
6. Текст без якорей → пустые списки, не падение.
7. Прогон по всем черновикам из `tests/drafts/` без исключений.

### DoD ML-03

Общий DoD + на 10 тестовых черновиках якоря извлекаются без ложных
срабатываний на обычных числах.

# ML-04. Fact Guard

**Ветка:** `ml/04-fact-guard`
**Источник истины:** `contracts/llm_contract.md` §5
**Блокируется:** ML-03
**Приоритет:** P0 — **сценарий 4 и главный козырь на защите**

### 4.1. Зачем это вообще

Все команды напишут в промпте «не выдумывай». Мы это **проверяем
детерминированным кодом** после модели.

Даёт баллы сразу в четырёх местах: качество ИИ-обработки, сценарий 4 в
разделе 5, сценарий 4 в разделе 6, техническая проверяемость.

### 4.2. Сверка

```python
def check(source_anchors: dict, result_anchors: dict) -> GuardResult
```

| Результат | `verdict` | Что дальше |
|---|---|---|
| `added` пуст, `lost` пуст | `clean` | принять |
| `added` пуст, `lost` непуст | `warning` | принять, фронт предупредит |
| `added` непуст | `blocked` | перегенерация, затем fallback |

### 4.3. Почему `lost` — предупреждение, а не блокировка

Модель может законно убрать якорь: вычистить эмоциональную вставку, а
внутри неё было число. Блокировать за это — получать ложные
срабатывания на каждом втором черновике.

`added` — другое дело. Появление даты, которой не было в черновике, это
ровно та галлюцинация, которую проверяет сценарий 4. Здесь блокируем
без компромиссов.

### 4.4. Перегенерация

При `blocked` — **одна** повторная попытка с усиленным промптом
(добавляется строка о конкретном выдуманном якоре). Если снова
`blocked` — уход в fallback с `is_fallback: true`.

Не зацикливаться: две попытки максимум, иначе на CPU это три минуты
ожидания.

### 4.5. Ответ бэкенду

```json
"fact_guard": {
  "verdict": "clean",
  "preserved": ["10 июня 2025", "14 календарных дней"],
  "lost": [],
  "added": [],
  "source_count": 2,
  "preserved_count": 2
}
```

`source_count` и `preserved_count` фронт превращает в бейдж «Сохранено
2 из 2 фактов · Добавлено 0».

### 4.6. Тесты

1. Модель сохранила всё → `verdict=clean`.
2. Модель дописала дату, которой не было → `verdict=blocked`.
3. После блокировки идёт ровно одна перегенерация.
4. Две блокировки подряд → `is_fallback=true`.
5. Модель убрала якорь → `verdict=warning`, результат принят.
6. `Иванов И.И.` → `Иванов И. И.` не считается потерей.
7. `preserved_count` и `source_count` совпадают при `clean`.
8. Текст без якорей → `clean`, счётчики по нулям.

### DoD ML-04

Общий DoD + подготовлен черновик, на котором Guard ловит галлюцинацию,
и это можно показать эксперту в `/api/trace/{id}`.

# ML-05. Rule-based fallback

**Ветка:** `ml/05-fallback`
**Источник истины:** `contracts/llm_contract.md` §4;
`flows.md` «Сценарий 6»
**Блокируется:** ML-02
**Приоритет:** P0 — часть сценария 6

### 5.1. Когда включается

- модель не ответила после retry и repair
- Fact Guard дважды вернул `blocked`
- Ollama недоступна, а `fallback_enabled = true`

### 5.2. Что делает

Три слоя, без модели вообще:

1. **Спелчекер** — `pyspellchecker` или `hunspell` с русским словарём
2. **Словарь просторечий** — 30–50 пар замен: «задолбался» → удалить,
   «типа» → удалить, «надо» → «необходимо», «хочу» → «прошу»
3. **Шаблонная структуризация** — по `structure_hint` из запроса

Извлечение реквизитов в fallback — регулярками из `anchors.py` плюс
простые эвристики («Прошу... Директору X» → адресат).

### 5.3. Честность

```json
{"is_fallback": true, "model_version": "rule-based-1.0"}
```

Бэкенд по этому флагу ставит документу статус `degraded`, фронт
показывает плашку «обработано в резервном режиме».

**Не притворяться, что всё хорошо.** Критерий прямо требует: ошибка не
должна выглядеть как успех.

### 5.4. Fact Guard работает и здесь

`fact_guard` заполняется даже при `is_fallback: true`. Rule-based слой
по определению ничего не выдумывает, так что вердикт будет `clean` —
но поле должно быть на месте, бэкенд его ждёт.

### 5.5. Тесты

1. Ollama остановлена → `/process` отвечает 200 с `is_fallback=true`.
2. Орфографическая ошибка исправлена спелчекером.
3. Просторечие удалено словарём.
4. Якоря в fallback-результате сохранены полностью.
5. `fact_guard.verdict == "clean"` при fallback.
6. `improved_text` непустой даже на коротком черновике.
7. `requisites` содержит все ключи из `requisite_keys`.

### DoD ML-05

Общий DoD + `docker compose stop ollama`, отправка черновика, получение
осмысленного результата с честным флагом.

# ML-06. Набор тестовых черновиков

**Ветка:** `ml/06-test-drafts`
**Источник истины:** `contracts/llm_contract.md` §6
**Блокируется:** ML-04
**Приоритет:** P1

### 6.1. Зачем три раза

Один набор данных закрывает три разные задачи:

- материал для демо — UI берёт оттуда черновики для кнопок на главной
- доказательство для критерия 4.4 «техническая проверяемость», 3 балла
- защита от регрессий при правках промпта

### 6.2. Формат

```
tests/drafts/03_no_addressee.txt
tests/drafts/03_no_addressee.expected.json
```

```json
{
  "doc_type": "memo",
  "requisites_must_be_null": ["addressee"],
  "anchors_must_survive": ["14 календарных дней", "10 июня 2025"],
  "anchors_must_not_appear": ["Иванов", "№"],
  "fact_guard_verdict": "clean"
}
```

Проверяем **структурные утверждения**, а не точный текст: он будет
разным при каждом прогоне, и тест на точное совпадение будет падать
всегда.

### 6.3. Минимальный набор

| Файл | Что проверяет |
|---|---|
| `01_clean.txt` | сценарий 1, чистый черновик |
| `02_typos_slang.txt` | сценарий 2, ошибки и просторечия |
| `03_no_addressee.txt` | сценарий 3, пропущенный реквизит |
| `04_facts.txt` | сценарий 4, даты и суммы |
| `05_report.txt` | докладная записка |
| `06_reference.txt` | информационная справка |
| `07_letter.txt` | письмо |
| `08_long.txt` | 3000+ символов |
| `09_minimal.txt` | две строки, почти нет данных |
| `10_hallucination_bait.txt` | текст, провоцирующий выдумывание |

Последний — самый ценный. На нём показываем Fact Guard в действии.

### 6.4. Тесты

1. Все 10 черновиков обрабатываются без исключений.
2. Каждый `expected.json` выполняется.
3. Прогон всего набора укладывается в 15 минут на CPU.
