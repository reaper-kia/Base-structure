# Контракт ИИ-слоя (ml_service)

**Владельцы:** ML (реализует), TL (потребляет). Правки — только через TL.

Два уровня контракта, которые легко спутать:

1. **HTTP-контракт** между бэкендом и `ml_service` — стабильный, описан в разделе 2.
2. **Контракт модели** — что языковая модель обязана вернуть в ответ на промпт.
   Описан в разделе 3 и продублирован машиночитаемо в `llm_schema.json`.

Второй контракт ненадёжен по своей природе: 7B-модель ломает JSON. Поэтому между
ними стоит слой ремонта и валидации, описанный в разделе 4.

---

## 1. Почему ml_service — отдельный контейнер

Можно было положить вызов модели прямо в бэкенд. Не кладём, и вот зачем:

**Критерий 3.1** требует, чтобы ИИ-обработка и генерация DOCX были «логически
разделены и имели понятные границы ответственности». Отдельный процесс с
собственным HTTP-контрактом — это граница, которую видно, а не которую надо
объяснять словами.

**Сценарий 6** демонстрируется одной командой: `docker compose stop ml_service`.
Эксперт видит, что бэкенд жив, черновик цел, сообщение понятное. Если бы модель
жила внутри бэкенда, «имитировать недоступность ИИ-компонента» пришлось бы
подделывать флагом — менее убедительно.

**Критерий «готовность к развитию»** требует возможности «заменять или настраивать
ИИ-компонент». Замена Ollama на внешний API или на другую модель — это правка
внутри `ml_service`, бэкенд не трогается вообще.

Цена: один HTTP-хоп, +5 мс к запросу, который и так идёт десятки секунд.

## 2. HTTP-контракт

### `POST /api/v1/process`

```json
{
  "draft": "прошу предоставить мне ежегодный оплачиваемый отпуск с 10 июня 2025 сроком на 14 календарных дней, а то я уже задолбался",
  "doc_type": "memo",
  "doc_type_name": "Служебная записка",
  "structure_hint": "кому -> от кого -> суть -> просьба -> подпись",
  "requisite_keys": ["addressee", "author", "position", "subject", "doc_date"],
  "request_id": "3f2b9c10-..."
}
```

**Ключевое решение: `ml_service` ничего не знает про типы документов.**

Бэкенд читает `doc_types/*.yaml` и передаёт в запросе всё нужное: человеческое
название типа, подсказку по структуре и список ключей реквизитов, которые надо
попытаться извлечь. `ml_service` подставляет это в промпт и валидирует ответ по
присланному списку ключей.

Почему так: добавление пятого типа документа (например, приказа) должно быть
правкой одного YAML-файла на бэкенде. Если бы `ml_service` тоже читал конфиги
типов, они бы разъехались, и добавление типа стало бы правкой в двух сервисах.
Это ровно то, что критерий «готовность к развитию» называет расширяемостью.

| Поле | Тип | Обязательно | Примечание |
|---|---|---|---|
| `draft` | string | да | 1–20000 символов |
| `doc_type` | string | да | технический id, идёт в логи и трейс |
| `doc_type_name` | string | да | подставляется в промпт |
| `structure_hint` | string | да | подставляется в промпт |
| `requisite_keys` | string[] | да | ровно эти ключи должны быть в ответе |
| `request_id` | string | нет | сквозной id для сопоставления логов |

### Ответ `200 OK`

```json
{
  "improved_text": "Прошу предоставить ежегодный оплачиваемый отпуск с 10 июня 2025 года сроком на 14 календарных дней.",
  "requisites": {
    "addressee": null,
    "author": null,
    "position": null,
    "subject": "О предоставлении отпуска",
    "doc_date": null
  },
  "changes": [
    {"type": "style", "from": "а то я уже задолбался", "to": ""},
    {"type": "structure", "from": "", "to": "О предоставлении отпуска"}
  ],
  "fact_guard": {
    "verdict": "clean",
    "preserved": ["10 июня 2025", "14 календарных дней"],
    "lost": [],
    "added": [],
    "source_count": 2,
    "preserved_count": 2
  },
  "is_fallback": false,
  "model_version": "qwen2.5:7b-instruct",
  "latency_ms": 18432.5
}
```

Гарантии, которые `ml_service` даёт бэкенду:

- `requisites` содержит **ровно** ключи из `requisite_keys` — ни больше, ни меньше.
  Отсутствующее значение — это `null`, а не пустая строка и не пропущенный ключ.
- `fact_guard` заполнен всегда, даже при `is_fallback: true`.
- `improved_text` непустой. Если модель вернула пустоту, `ml_service` уходит в
  fallback и возвращает результат rule-based слоя.

### Ответ `503 Service Unavailable`

```json
{"detail": "Модель недоступна и fallback отключён"}
```

Возвращается, только если `fallback_enabled = false` в конфиге `ml_service`.
В боевом режиме fallback включён, и этого кода быть не должно — но бэкенд обязан
его пережить: `HttpLLMClient` ловит любой не-2xx и превращает в `LLMUnavailable`.

### `GET /health` и `GET /health/model`

`/health` всегда `200`, даже без модели — это осознанно, как и в исходном
бойлерплейте. Иначе Docker будет перезапускать контейнер, который на самом деле
работоспособен в режиме деградации.

```json
GET /health/model  ->
{
  "model_loaded": true,
  "model_version": "qwen2.5:7b-instruct",
  "fallback_enabled": true,
  "supported_tasks": ["process"]
}
```

Дёргается перед демонстрацией и отдаётся бэкендом в `GET /api/dev/state`.

## 3. Контракт модели

Это то, что языковая модель обязана вернуть в ответ на промпт. Машиночитаемая
версия — `llm_schema.json`, она же уходит в Ollama как `format`.

```json
{
  "improved_text": "string, непустой",
  "requisites": {
    "<ключ из requisite_keys>": "string | null"
  },
  "changes": [
    {
      "type": "spelling | punctuation | style | structure",
      "from": "string",
      "to": "string"
    }
  ]
}
```

`fact_guard`, `is_fallback`, `model_version` и `latency_ms` модель **не заполняет** —
их добавляет `ml_service` уже после проверки. Модель не может свидетельствовать
о собственной честности.

### 3.1. Промпт

Живёт в `ml_service/src/ml_service/llm/prompts/process.txt`, версионируется в git.
Правки промпта — обычный коммит с понятным сообщением, чтобы на защите можно было
показать историю.

Обязательные блоки промпта, в порядке следования:

1. **Роль.** Одна строка. «Ты — помощник делопроизводителя.»
2. **Запрет на выдумывание.** Явный перечень: даты, ФИО, должности, номера, суммы,
   названия организаций. Формулировка «если сведения нет — ставь null», а не
   «постарайся не выдумывать».
3. **Тип и структура.** Подставляются `doc_type_name` и `structure_hint` из запроса.
4. **Формат ответа.** Скелет JSON с нужными ключами. Явно: «только JSON, без
   пояснений и без markdown-ограждений».
5. **Few-shot: два примера.** Один — черновик со всеми реквизитами. Второй —
   черновик **без адресата**, где в ответе стоит `null`. Второй пример обязателен:
   без него модель склонна выдумывать правдоподобного адресата, и сценарий 3
   разваливается.
6. **Исходный текст.**

Температура `0.2`. Выше — модель начинает «улучшать» факты.

### 3.2. Что считается нарушением контракта модели

| Нарушение | Реакция `ml_service` |
|---|---|
| Невалидный JSON | repair-проход, затем 2 retry, затем fallback |
| Лишний ключ в `requisites` | выбросить молча |
| Отсутствующий ключ из `requisite_keys` | добавить со значением `null` |
| Пустая строка вместо `null` | нормализовать в `null` |
| `improved_text` пустой | fallback |
| `changes` отсутствует | подставить `[]`, не ошибка |
| Fact Guard вернул `blocked` | одна перегенерация, затем fallback |

Философия: `changes` — украшение, его потеря не ломает продукт. `improved_text`
и `requisites` — суть, их потеря означает провал обработки.

## 4. Слой надёжности

Между «модель ответила» и «вернули бэкенду» стоит четыре шага. Все — в
`registry.py`.

### Шаг 1. Запрос с принуждением к JSON

Ollama вызывается с `format` = содержимое `llm_schema.json`. Это не гарантия, но
резко повышает долю валидных ответов.

### Шаг 2. Repair-проход

Если `json.loads` упал, делаем второй вызов модели с коротким промптом «почини
этот JSON, верни только JSON» и сырым ответом. Дёшево и ловит больше половины
случаев — обычно модель просто обернула ответ в ```` ```json ````.

Перед repair пробуем дешёвую починку регуляркой: срезать markdown-ограждения и
всё до первой `{` и после последней `}`. Часто этого достаточно, и второй вызов
модели не нужен.

### Шаг 3. Fact Guard

Описан в разделе 5. Работает на детерминированном коде, не на модели.

### Шаг 4. Fallback

Если после retry и repair валидного ответа нет, или Fact Guard дважды вернул
`blocked`, включается `fallback.py`: локальный спелчекер плюс словарь просторечий
плюс шаблонная структуризация по `structure_hint`.

Возвращается честный `is_fallback: true`. Бэкенд по этому флагу ставит документу
статус `degraded`, фронт показывает плашку «обработано в резервном режиме».

**Гейт для ML на третьем часу работы:** прогнать 20 черновиков и замерить долю
валидных JSON после шага 1.

- ≥90% — идём по плану
- 70–90% — repair обязателен, всё равно идём по плану
- <70% — **писать в чат немедленно**, переходим на план Б

**План Б:** модель отвечает не JSON, а размеченным текстом
(`<TEXT>...</TEXT><ADDRESSEE>...</ADDRESSEE>`), парсим регулярками. HTTP-контракт
из раздела 2 при этом **не меняется** — бэкенд ничего не заметит. В этом и смысл
отдельного сервиса.

## 5. Fact Guard

Детерминированная защита от галлюцинаций. Не промпт, а код.

**Сценарий 4**, критерий «качество ИИ-обработки», критерий 4.4 «техническая
проверяемость». Все команды напишут в промпте «не выдумывай». Мы это проверяем.

### 5.1. Якоря

`guard/anchors.py` извлекает из текста пять категорий:

| Категория | Что ловит | Примеры |
|---|---|---|
| `date` | даты в цифровом и словесном виде | `10.06.2025`, `10 июня 2025` |
| `amount` | числа с единицами | `14 календарных дней`, `50 000 руб.` |
| `fio` | ФИО полностью и с инициалами | `Иванов И.И.`, `Петров Пётр Петрович` |
| `number` | регистрационные номера | `№ 15`, `№ 47/2-К` |
| `org` | названия в кавычках | `«Ромашка»` |

Регулярки, не NER. Они дают 80% результата за 20% времени, а Natasha добавляется
сверху позже, если останется время. Важно: категория не должна быть слишком
жадной — если регулярка на `amount` поймает каждое число в тексте, Fact Guard
начнёт блокировать нормальные переформулировки.

### 5.2. Сверка

```python
def check(source_anchors: dict, result_anchors: dict) -> GuardResult
```

Сравнение по нормализованным строкам: нижний регистр, схлопнутые пробелы,
убранные точки в инициалах. Без нормализации `Иванов И.И.` и `Иванов И. И.`
посчитаются разными, и Guard выдаст ложное срабатывание.

| Результат сверки | `verdict` | Что дальше |
|---|---|---|
| `added` пуст, `lost` пуст | `clean` | принять |
| `added` пуст, `lost` непуст | `warning` | принять, фронт предупредит |
| `added` непуст | `blocked` | перегенерация, затем fallback |

### 5.3. Почему `lost` — это предупреждение, а не блокировка

Модель может законно убрать якорь: например, вычистить эмоциональную вставку,
внутри которой было число. Блокировать за это — значит получать ложные
срабатывания на каждом втором черновике.

`added` — другое дело. Появление даты, которой не было в черновике, это ровно
то нарушение, которое задание называет галлюцинацией, и сценарий 4 проверяет
именно его. Здесь блокируем без компромиссов.

## 6. Что ML сдаёт вместе с кодом

Набор тестов в `ml_service/tests/drafts/` — 10–15 черновиков разного качества и
ожидаемые структурные результаты. Не точный текст (он будет разным при каждом
прогоне), а проверяемые утверждения:

```
drafts/03_no_addressee.txt
drafts/03_no_addressee.expected.json
{
  "requisites_must_be_null": ["addressee"],
  "anchors_must_survive": ["14 календарных дней", "10 июня 2025"],
  "anchors_must_not_appear": ["Иванов", "№"],
  "fact_guard_verdict": "clean"
}
```

Это одновременно материал для демо (UI-дизайнер берёт оттуда черновики для
кнопок на главной), доказательство для критерия 4.4 и защита от регрессий при
правках промпта.
