# Контракт REST API

**Владельцы:** TL (реализует), FE (потребляет). Правки — только через TL.
**Статус:** зафиксирован. Пока файл не изменён, обе стороны пишут код против него.

Базовый префикс — `/api`. Все тела запросов и ответов — JSON в UTF-8,
кроме `POST /documents/{id}/render`, который отдаёт бинарный DOCX.

---

## 0. Три решения, которые определяют весь контракт

### 0.1. Обработка асинхронная, фронт опрашивает состояние

`POST /api/documents` **не ждёт** окончания ИИ-обработки. Он создаёт документ,
запускает фоновую задачу и сразу возвращает `202` со статусом `processing`.
Фронт опрашивает `GET /api/documents/{id}` раз в секунду, пока статус не станет
терминальным.

Почему не синхронно: локальная 7B-модель на CPU отвечает 20–90 секунд. Синхронный
запрос упрётся в таймаут nginx (по умолчанию 60 с) и в таймаут браузера, причём
упрётся именно на демонстрации, когда эксперт смотрит на экран. Плюс критерий
раздела 6 требует, чтобы пользователь понимал текущий этап — а прогресс по стадиям
можно показать только при опросе.

Цена решения: FE пишет поллинг. Это 15 строк в хуке.

### 0.2. Черновик неизменяем

Поле `draft` записывается один раз при создании и не перезаписывается **никогда** —
ни при ошибке ИИ, ни при ручных правках, ни при повторной обработке. Улучшенный
текст живёт отдельно в `improved_text`.

Прямое требование сценария 6: «сервис не теряет введённый пользователем текст».
Если бы мы писали результат ИИ поверх черновика, любая ошибка на втором проходе
уничтожила бы оригинал.

### 0.3. Ошибка ИИ — это не HTTP-ошибка

Недоступность ИИ-компонента возвращается как `200 OK` с
`status: "failed"` и заполненным полем `error`. HTTP-коды 4xx/5xx используются
только для транспортных и валидационных проблем (документ не найден, тело запроса
кривое).

Почему: ошибка ИИ — это штатное состояние документа, а не сбой API. Фронту нужно
показать черновик, сообщение и кнопку «Повторить» — то есть отрисовать состояние,
а не обработать исключение. Если бы мы отдавали 503, FE пришлось бы отдельно
вытаскивать черновик из тела ошибки.

Список четырёх обязательных типов документов с их реквизитами. Источник данных —
`src/modules/documents/config/doc_types/*.yaml`.

**Сценарий 5** (типы и шаблоны), **сценарий 3** (фронт заранее знает, какие поля
обязательны, и может отрисовать панель реквизитов до ответа ИИ).

```
200 OK
[
  {
    "id": "memo",
    "name": "Служебная записка",
    "description": "Внутренний документ с просьбой или предложением",
    "requisites": [
      {"key": "addressee", "label": "Адресат", "required": true},
      {"key": "author", "label": "Автор", "required": true},
      {"key": "position", "label": "Должность автора", "required": true},
      {"key": "subject", "label": "Заголовок к тексту", "required": true},
      {"key": "doc_date", "label": "Дата документа", "required": true}
    ]
  },
  { "id": "report", "name": "Докладная записка", ... },
  { "id": "reference", "name": "Информационная справка", ... },
  { "id": "letter", "name": "Письмо", ... }

```

Порядок типов в массиве — порядок отображения на фронте. Не сортировать на клиенте.

Список шаблонов оформления. Источник — `src/modules/templates/assets/*/rules.yaml`.

**Сценарий 5.** Поле `preview_url` ведёт на статичный PNG, который рисует UI-дизайнер;
генерировать превью на лету не требуется.

```
200 OK
[
  {
    "id": "classic",
    "name": "Классический",
    "description": "ГОСТ-подобное оформление: Times New Roman 14, поля 30 мм",
    "preview_url": "/static/templates/classic.png",
    "available": true
  },
  {
    "id": "modern",

    "preview_url": "/static/templates/modern.png",
```

`available: false` означает, что папка шаблона повреждена или отсутствует. Фронт

## 2. Жизненный цикл документа

### `POST /api/documents`

Создаёт документ и запускает обработку. **Сценарий 1**, шаг запуска.

```
Запрос:
{
  "draft": "прошу предоставить мне ежегодный оплачиваемый отпуск с 10 июня 2025 ...",
  "doc_type": "memo",
  "template_id": "classic"
}
```

| Поле | Ограничения |
|---|---|
| `draft` | 1–20000 символов, непустой после `strip()` |
| `doc_type` | один из id из `GET /api/doc-types` |
| `template_id` | один из id из `GET /api/templates` |

```
202 Accepted
{
  "id": "3f2b9c10-...",
  "status": "processing",
  "draft": "прошу предоставить мне ...",
  "doc_type": "memo",
  "template_id": "classic",
  "stage": "llm",
  "improved_text": null,
  "changes": [],
  "requisites": [],
  "fact_guard": null,
  "error": null
}
```

Ошибки: `422` при нарушении ограничений выше (стандартный формат FastAPI,
фронтовый `client.ts` уже умеет его разбирать).

### `GET /api/documents/{id}`

Текущее состояние. Опрашивается фронтом раз в секунду, пока `status == "processing"`.

```
200 OK  — тот же объект DocumentState, что описан ниже
404 Not Found — {"detail": "Документ не найден"}
```

## 3. Объект DocumentState

Единственная структура, которой обмениваются фронт и бэкенд. Возвращается из
`POST /documents`, `GET /documents/{id}`, `PATCH /requisites` и `POST /reprocess`.

```json
{
  "id": "3f2b9c10-...",
  "status": "processed",
  "stage": null,
  "doc_type": "memo",
  "template_id": "classic",
  "draft": "исходный текст пользователя, никогда не меняется",
  "improved_text": "Прошу предоставить ежегодный оплачиваемый отпуск ...",
  "changes": [
    {"type": "spelling", "from": "заявленее", "to": "заявление"},
    {"type": "style", "from": "а то я уже задолбался", "to": ""}
  ],
  "requisites": [
    {"key": "addressee", "label": "Адресат", "value": null,
     "status": "missing", "required": true},
    {"key": "doc_date", "label": "Дата документа", "value": "11.09.2026",
     "status": "auto_filled", "required": true}
  ],
  "fact_guard": {
    "verdict": "clean",
    "preserved": ["10 июня 2025", "14 календарных дней"],
    "lost": [],
    "added": [],
    "source_count": 2,
    "preserved_count": 2
  },
  "is_fallback": false,
  "error": null
}
```

### 3.1. `status` — терминальное состояние документа

| Значение | Когда | Что делает фронт |
|---|---|---|
| `processing` | обработка идёт | крутит прогресс по `stage`, продолжает поллинг |
| `processed` | ИИ отработал нормально | показывает diff и панель реквизитов |
| `degraded` | ИИ упал, сработал rule-based слой | то же + плашка «обработано в резервном режиме» |
| `failed` | упало всё, включая fallback | показывает черновик, `error.message`, кнопку «Повторить» |

`degraded` и `failed` — разные вещи, и это важно для **сценария 6**. Критерий
говорит: ошибка не должна выглядеть как успех. Поэтому `degraded` — это честный
результат с пометкой, а не тихая подмена. Документ при `degraded` сформировать
можно; при `failed` — нельзя, `render` вернёт `409`.

### 3.2. `stage` — этап внутри обработки

Заполнено только при `status == "processing"`, иначе `null`.

Значения по порядку: `"llm"` → `"fact_guard"` → `"validation"`.

Фронт переводит их в человеческие подписи: «обрабатываем текст» → «проверяем факты»
→ «проверяем реквизиты». Это напрямую закрывает критерий раздела 6 — пользователь
понимает текущий этап, а не смотрит на безликий спиннер.

### 3.3. `changes[]` — что изменила система

**Сценарии 2 и 4**, и особенно критерий демонстрации: «объяснить, что изменила
система».

```json
{"type": "spelling", "from": "заявленее", "to": "заявление"}
```

`type` — одно из: `spelling`, `punctuation`, `style`, `structure`.
Фронт красит правку в diff цветом по типу и показывает легенду.

Пустая строка в `to` означает удаление фрагмента (например, вычищенная
эмоциональность). Пустая строка в `from` означает вставку — допустима только
для структурных элементов вроде заголовка блока, но **никогда** для фактов.

`changes` — вспомогательные данные для подсветки, а не источник истины. Истина —
`improved_text`. Если модель вернула кривой `changes`, фронт всё равно строит diff
алгоритмически по паре `draft` / `improved_text`, а `changes` использует только
для классификации типа правки.

### 3.4. `requisites[]` — панель реквизитов

**Сценарий 3.** Массив в порядке, заданном в `doc_types/*.yaml`. Не сортировать.

| `status` | Значение | Откуда | Как показывает фронт |
|---|---|---|---|
| `found_in_draft` | есть | ИИ извлёк из черновика | зелёный чип |
| `user_provided` | есть | пользователь ввёл в PATCH | синий чип |
| `auto_filled` | есть | правило `auto_fillable` | серый чип + подпись «подставлено системой» |
| `missing` | `null` | не найдено, пользователь не решал | жёлтый чип, кнопки «Указать» / «Оставить пустым» |
| `left_blank` | `null` | пользователь явно выбрал «оставить пустым» | серый чип + подпись «будет помечено в документе» |

Разделение `missing` и `left_blank` — не формальность. Критерий 6.3 требует, чтобы
пользователь «не оставался в неопределённости относительно незаполненных данных».
`missing` — система ждёт решения. `left_blank` — решение принято. В DOCX оба
рендерятся одинаково, как `[Адресат]` с жёлтой заливкой, но в интерфейсе это разные
состояния, и жёлтых чипов, требующих внимания, после решения пользователя не
остаётся.

**Система не имеет права проставить значение сама**, кроме случаев из
`auto_fillable` в `doc_types/*.yaml`. Сейчас там единственное правило — `doc_date: today`.
Содержательные даты (дата события, дата начала отпуска) под это правило не подпадают
и остаются `missing`.

### 3.5. `fact_guard` — доказательство, что ничего не выдумано

**Сценарий 4**, критерий «качество ИИ-обработки», критерий «техническая
проверяемость».

```json
{
  "verdict": "clean",
  "preserved": ["10 июня 2025", "14 календарных дней"],
  "lost": [],
  "added": [],
  "source_count": 2,
  "preserved_count": 2
}
```

| `verdict` | Смысл | Что сделал бэкенд |
|---|---|---|
| `clean` | ничего не добавлено, ничего не потеряно | принял результат |
| `warning` | часть якорей пропала | принял результат, фронт показывает предупреждение |
| `blocked` | появился якорь, которого не было в черновике | перегенерировал один раз; если снова `blocked` — вернул черновик со статусом `degraded` |

Фронт рисует бейдж: «Сохранено 2 из 2 фактов · Добавлено 0» — числа берутся из
`preserved_count` и `source_count`, длина `added`.

### 3.6. `error` — понятная ошибка

`null` при любом статусе, кроме `failed`.

```json
{
  "code": "llm_unavailable",
  "message": "ИИ-компонент недоступен. Черновик сохранён, попробуйте ещё раз.",
  "recoverable": true
}
```

| `code` | Когда |
|---|---|
| `llm_unavailable` | ml_service не отвечает, таймаут, включён тумблер отказа |
| `llm_invalid_response` | модель вернула нечитаемый JSON после retry и repair |
| `template_missing` | шаблон повреждён, и запасной тоже недоступен |
| `internal` | всё остальное |

`message` — **на русском, для человека**. Никаких стектрейсов, никаких
`HTTPError 502`. Этот текст эксперт увидит на экране в сценарии 6, и по нему
ставится балл.

`recoverable: true` означает, что имеет смысл показать кнопку «Повторить».

## 4. Работа с реквизитами и генерация

### `PATCH /api/documents/{id}/requisites`

**Сценарий 3.** Пользователь заполняет недостающее или явно отказывается заполнять.

```
Запрос:
{
  "values": {
    "addressee": "Директору ООО «Ромашка» Петрову П.П.",
    "position": null
  }
}
```

Правила обработки:

- непустая строка → `value` = строка, `status` = `user_provided`
- `null` → `value` остаётся `null`, `status` = `left_blank`
- ключ, которого нет в схеме типа документа → игнорируется молча
- ключи, не упомянутые в запросе, не трогаются

```
200 OK — обновлённый DocumentState
404 Not Found — документ не найден
409 Conflict — документ в статусе processing, состояние ещё меняется
```

Метод именно `PATCH`, а не `PUT`: фронт присылает только те поля, которые
пользователь тронул. Это позволяет заполнять реквизиты по одному, не гоняя
весь массив.

### `POST /api/documents/{id}/render`

**Сценарий 1**, финальный шаг. Отдаёт бинарный DOCX.

```
200 OK
Content-Type: application/vnd.openxmlformats-officedocument.wordprocessingml.document
Content-Disposition: attachment; filename="sluzhebnaya-zapiska-11-09-2026.docx"
<бинарные данные>
```

```
409 Conflict — {"detail": "Документ ещё не обработан"}   (status == processing или failed)
404 Not Found
```

Имя файла — транслитерация названия типа документа плюс дата. Кириллицу в
`Content-Disposition` не отдаём: старые версии Safari её ломают.

**Поведение при повреждённом шаблоне** (вторая половина п. 2.3 задания): рендерер
не падает. Он берёт запасной шаблон из `settings.default_template_id`, формирует
документ и добавляет в заголовок ответа:

```
X-Template-Fallback: true
X-Template-Fallback-Reason: Шаблон «modern» повреждён, применён «classic»
```

Фронт читает заголовок и показывает плашку. Документ пользователь при этом
получает — это и есть «корректно обработать ситуацию» из задания.

### `POST /api/documents/{id}/reprocess`

**Сценарий 6**, кнопка «Повторить».

Запускает обработку заново на том же неизменном `draft`. Реквизиты со статусом
`user_provided` и `left_blank` **сохраняются** — пользователь уже потратил на них
время, заставлять вводить заново нельзя.

```
202 Accepted — DocumentState со status: "processing"
404 Not Found
409 Conflict — уже обрабатывается
```

## 5. Проверяемость и демонстрация

### `GET /api/trace/{id}`

Журнал обработки. Критерий 4.4 «Техническая проверяемость обработки и генерации»,
до 3 баллов. Эксперт видит внутреннюю логику без обращения к команде.

```
200 OK
[
  {"stage": "anchors",     "payload": {"date": ["10 июня 2025"], "amount": ["14 календарных дней"]}},
  {"stage": "llm_request", "payload": {"prompt": "Ты — помощник делопроизводителя...", "doc_type": "memo"}},
  {"stage": "llm_raw",     "payload": {"improved_text": "...", "requisites": {...}}},
  {"stage": "fact_guard",  "payload": {"verdict": "clean", "added": [], "lost": []}},
  {"stage": "validation",  "payload": {"missing": ["addressee"], "auto_filled": ["doc_date"]}},
  {"stage": "render",      "payload": {"template_id": "classic", "rules_applied": {"font": "Times New Roman", "size_pt": 14}}}
]
```

Хранится in-memory, при рестарте теряется — это допустимо, БД для журнала не нужна.
Эндпоинт открытый, без авторизации: эксперт должен пройти всё сам.

### `POST /api/dev/break-ai`

**Сценарий 6.** Тумблер имитации отказа ИИ, доступный эксперту.

```
Запрос:  {"enabled": true}
Ответ:   200 OK  {"ai_force_failure": true}
```

Переключает `settings.ai_force_failure` в рантайме. Пока включён, `HttpLLMClient`
сразу кидает `LLMUnavailable`, не ходя в сеть.

Эндпоинт **не прячем** за паролем и не убираем из прода. Смысл именно в том, чтобы
эксперт сломал сервис своими руками и убедился, что черновик цел, а сообщение
понятное. Большинство команд будет рассказывать про обработку ошибок словами;
мы даём кнопку.

### `GET /api/dev/state`

```
200 OK
{
  "ai_force_failure": false,
  "ml_service_url": "http://ml_service:8100",
  "ml_reachable": true,
  "model_version": "qwen2.5:7b-instruct",
  "templates_loaded": ["classic", "modern"]
}
```

Нужен фронту, чтобы правильно отрисовать положение тумблера после перезагрузки
страницы, и команде — чтобы за секунду понять перед демо, всё ли поднялось.

## 7. Что фронт должен мокать до готовности бэкенда

Порядок появления эндпоинтов на бэкенде: `doc-types` и `templates` (час 3),
`POST /documents` + `GET /documents/{id}` с фиктивной обработкой (час 6),
`render` (час 10), `PATCH` и `reprocess` (час 14), `trace` и `dev/*` (час 18).

До этого FE работает на `mockApi.ts`, отдающем те же структуры с задержкой
1.5 секунды и возможностью переключить сценарий: «всё найдено», «нет адресата»,
«ИИ упал». Переключатель мока — три константы, а не три ветки кода.
