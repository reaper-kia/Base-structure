# Doc3 — ИИ-конструктор служебных документов

Сервис превращает черновой текст (напечатанный или надиктованный) в готовый
редактируемый DOCX-документ: исправляет орфографию и стиль, приводит текст к
официально-деловому оформлению, проверяет обязательные реквизиты и
программно применяет правила выбранного шаблона.

**Путь пользователя — три шага:**

1. **Ввод черновика** — вручную, из буфера обмена или голосом.
2. **Выбор типа документа и шаблона оформления** — 4 обязательных типа
   (служебная записка, докладная записка, информационная справка, письмо),
   не менее 2 шаблонов на каждый.
3. **Обработка и скачивание** — ИИ улучшает текст и извлекает реквизиты,
   пользователь уточняет недостающие данные, система собирает DOCX.

## Стек и почему так

| Слой | Технология | Почему |
|---|---|---|
| Backend | FastAPI + PostgreSQL + Redis | асинхронная обработка документа, кэш повторных запросов |
| ИИ | Ollama + qwen2.5:7b-instruct, локально | без внешних API — независимая проверка и запуск без ключей и затрат (критерий 3.4) |
| Распознавание речи | отдельный сервис на Vosk (`stt-service/`), локально | тот же принцип: без внешних сервисов распознавания |
| Frontend | React + Vite + TypeScript | |
| Генерация DOCX | `python-docx`, правила шаблона — код, не ИИ | оформление не должно зависеть от произвольного ответа модели (критерий 3.1) |

Содержание и оформление документа разделены архитектурно: ИИ работает только
с текстом и реквизитами, правила шаблона (шрифты, поля, колонтитулы,
расположение блоков) применяются отдельным программным модулем и не зависят
от того, что вернула модель.

## Быстрый старт

```bash
cp .env.example .env

make up            # app + db + redis + frontend + ollama + ml_service + stt_service
make pull-model     # обязательный первый шаг после первого запуска:
                    # скачивает веса модели (~5 ГБ) в постоянный том,
                    # без этого ИИ-обработка работает только в резервном режиме
make migrate        # применить миграции
make smoke          # end-to-end проверка: создать документ → дождаться → скачать DOCX
```

- Backend: http://localhost:8000 — Swagger на `/docs`
- Frontend: http://localhost:3000
- ML-сервис: http://localhost:8100/docs
- Сервис распознавания речи: http://localhost:8200/health

Проверка живости: `/health`, `/health/db`, `/health/redis` (backend),
`/health/model` (ML-сервис — отличает «процесс жив» от «модель реально
отвечает»).

**Боевой стенд:** `docker compose -f compose.prod.yml up --build -d`,
затем `make pull-model` тем же образом.

## Архитектура

```
черновик пользователя
      │
      ▼
[ИИ-обработка] ml_service (Ollama, qwen2.5:7b) ──► исправленный текст
      │                                             + извлечённые реквизиты
      │  (только текст и реквизиты, не оформление)
      ▼
[Валидация реквизитов] — обязательные поля по типу документа,
                          отсутствующие → запрос пользователю
                          или явная метка «[Заполнить]»
      │
      ▼
[Генератор DOCX] — программные правила выбранного шаблона
                    (шрифт, поля, колонтитулы, расположение блоков)
      │
      ▼
готовый .docx
```

Данные последовательно проходят между компонентами без потери исходных
сведений; правила оформления не зависят от произвольного ответа ИИ.

## Логика работы с ИИ и защита от галлюцинаций

- Модель получает черновик и структуру ожидаемого JSON-ответа (исправленный
  текст + извлечённые реквизиты), схема закреплена в `contracts/llm_schema.json`.
- Модели прямо запрещено добавлять факты, даты, фамилии и прочие сведения,
  которых не было в исходном тексте.
- Fact Guard (`ml_service/src/ml_service/guard/`) сверяет «якоря» (даты,
  суммы, ФИО) между черновиком и результатом.
  **Известное ограничение:** сейчас сравнение идёт по множеству найденных
  значений, а не по их привязке к субъекту и условию — перестановка суммы
  между двумя людьми или замена «после» на «до» может пройти проверку.
  Это не скрыто: пользователю всегда показывается diff черновика и результата,
  и решение остаётся за ним.
- Отсутствующий обязательный реквизит не подставляется моделью — он либо
  запрашивается у пользователя, либо помечается в документе явным текстом.

## Как добавить новый тип документа или шаблон

**Новый тип документа:**
1. Добавь YAML в `src/modules/documents/config/doc_types/` по образцу
   существующих — обязательные и необязательные реквизиты, их ключи и метки.
2. Используй канонические ключи реквизитов: `doc_date`, `position`,
   `signature`, `executor`, `addressee`, `author`, `subject`, `reg_number`
   (полный список и правило — `contracts/api.md` §3.4, `contracts/template_format.md`).
3. Зарегистрируй тип там, где перечислены остальные (`doc_type_registry.py`).

**Новый шаблон оформления:**
1. Каталог в `src/modules/templates/assets/<id>/` с `rules.yaml` и `template.docx`.
2. `rules.yaml` описывает поля страницы, шрифт, интервалы, колонтитулы и
   расположение каждого реквизита — используй те же канонические ключи,
   что и в схемах типов документов.
3. Шаблон подхватывается автоматически, без правок кода генератора.

## Что реализовано

- Полный путь: черновик → тип и шаблон → ИИ-обработка → реквизиты → DOCX.
- Диктовка черновика голосом (`stt-service/`, Vosk, полностью локально).
- Общий дедлайн обработки на документ (поле `deadline`), отделяющий
  «браузер перестал ждать» от «задание провалилось».
- Кэш результатов ИИ с коротким TTL для резервных (fallback) ответов —
  повтор после восстановления модели не залипает в старом результате.
- Имитация отказа ИИ (`POST /api/dev/break-ai`), изолированная по
  демонстрационной сессии — несколько экспертов не мешают друг другу.
- Журнал обработки по попытке (`GET /api/trace/{id}`): вход, версии модели и
  промпта, реальные длительности стадий, кэш-попадание, решения по реквизитам,
  применённый шаблон.
- CI: backend (lint + тесты), ML-сервис (lint + тесты), frontend (lint + тесты
  + сборка) — три независимых job.

## Известные ограничения

- Fact Guard проверяет якоря по множеству, не по их смысловой связи с
  субъектом и условием (подробнее — раздел выше).
- Демонстрационные черновики для интерфейса (`ml_service/tests/drafts/`) и
  материалы организаторов (`docs/`) — на момент этой записи каталоги пустые,
  наполняются отдельной задачей (ML-01 / TL-15.3).
- Публичный URL боевого стенда — см. плейсхолдер выше, требует заполнения
  перед защитой.

## Секреты

`.env` и `infra/ansible/inventory/group_vars/*/secrets.yml` в репозиторий не
попадают. Шаблоны — `.env.example` и `secrets.yml.example`. TLS-ключи для
локальной разработки — `make cert`.
