# Архитектура решения

## Одна идея, из которой следует всё остальное

Задание требует разделить работу с **содержанием** и с **оформлением**:
ИИ улучшает текст и выделяет реквизиты, а правила шаблона применяются
программно. Проверяется это сценарием 5: смена шаблона не должна поменять
ни одного слова, смена типа документа — ни одного шрифта.

Из этого требования выведены все границы в коде.

```
                        ┌──────────────┐
    браузер  ──────────▶│   frontend   │  nginx: SPA + прокси /api и /stt
                        └──────┬───────┘
    MAX-бот  ─────────────┐    │
                          ▼    ▼
                  ┌──────────────────────┐      ┌──────────────┐
                  │     backend (app)    │─────▶│  stt_service │  Vosk, локально
                  │                      │      └──────────────┘
                  │  modules/documents ──┼────▶ ┌──────────────┐   ┌────────┐
                  │  modules/templates   │      │  ml_service  │──▶│ ollama │
                  └──────────┬───────────┘      └──────────────┘   └────────┘
                             │
                    ┌────────┴─────────┐
                    │ Postgres   Redis │
                    └──────────────────┘
```

## Границы ответственности

| Компонент | Отвечает за | Не знает про |
|---|---|---|
| `modules/documents` | черновик, статусы, реквизиты, оркестрация пайплайна | шрифты, поля страницы, устройство модели |
| `modules/templates` | правила оформления, сборка DOCX | модель, статусы документа |
| `ml_service` | вызов модели, ремонт ответа, Fact Guard | типы документов, база, шаблоны |
| `stt_service` | распознавание речи | всё остальное |
| `frontend` | пользовательский путь | — |
| `bot` | тот же путь в мессенджере | — |

Проверка границы «рендерер не зависит от ИИ» автоматизирована:
`tests/unit/template/test_b2_07_template_switch.py` читает исходник
рендерера и падает, если там появится упоминание модели.

### Почему ml_service — отдельный контейнер

Вызов модели можно было положить прямо в бэкенд. Не положили, и вот зачем:

1. **Видимая граница.** Отдельный процесс с HTTP-контрактом — это граница,
   которую видно, а не которую надо объяснять словами.
2. **Сценарий 6 показывается одной командой.** `docker compose stop
   ml_service` — бэкенд жив, черновик цел, сообщение понятное. Внутри
   бэкенда «недоступность ИИ» пришлось бы подделывать флагом.
3. **Замена ИИ не трогает бэкенд.** Другая модель — переменная окружения,
   другой провайдер — правка одного файла в `ml_service`.

Цена: один HTTP-хоп, +5 мс к запросу, который и так идёт десятки секунд.

## Поток данных

```
POST /api/documents
   │  статус processing, deadline = now + 180 с
   ▼
фоновая задача
   │
   ├─ кэш Redis по sha256(черновик + тип + версия промпта)
   │     попадание → пропускаем модель целиком
   │
   ├─ ml_service POST /api/v1/process
   │     ├─ локальный RAG: vector search либо lexical fallback
   │     └─ Ollama с принуждением к JSON-схеме
   │        ├─ ответ не разобрался → починка регуляркой
   │        ├─ всё ещё нет        → repair-проход моделью
   │        └─ всё ещё нет        → резервная обработка правилами
   │
   ├─ Fact Guard: якоря черновика против якорей результата
   │     clean / warning / blocked
   │
   ├─ валидация реквизитов по YAML типа документа
   │     found_in_draft / auto_filled / missing
   │
   └─ статус processed либо degraded
```

Дальше пользователь при необходимости дозаполняет реквизиты
(`PATCH /requisites`), правит текст (`PATCH /text`) и скачивает файл
(`POST /render`). Ни одно из этих действий модель не вызывает.

## Решения и их цена

**Postgres, хотя задание допускает in-memory.** Обработка идёт до минуты,
и всё это время документ живёт в статусе `processing`. Если состояние
держать в памяти процесса, любой перезапуск теряет документ вместе с
черновиком — ровно то, что запрещает сценарий 6. Цена: контейнер базы и
одна миграция.

**Redis для кэша результатов.** Эксперт наверняка прогонит один и тот же
демо-черновик несколько раз. Без кэша каждый прогон — минута ожидания.
Ключ включает версию промпта: правка промпта автоматически инвалидирует
старые ответы.

**Дедлайн обработки хранится в базе, а не в памяти.** Проверку «не истёк
ли дедлайн» делает тот запрос, который первым увидел документ. Если
фоновая задача умерла вместе с процессом, документ всё равно уйдёт в
`failed` с понятным сообщением, а не зависнет в `processing` навсегда.

**Реквизиты — общий словарь ключей, набор задаёт тип.** Добавление пятого
типа документа — один YAML-файл. Ни бэкенд, ни ИИ-сервис, ни рендерер не
меняются: `ml_service` получает список ключей в запросе и ничего не знает
про типы.

**Журнал обработки — в памяти.** Он нужен для проверки и демонстрации, а
не для аудита: переживать перезапуск не обязан.

## Масштабирование и интеграции

Что уже готово к росту:

- обработка асинхронная, статус документа опрашивается — несколько
  пользователей не блокируют друг друга;
- тяжёлый вызов модели кэшируется по содержанию черновика;
- смена шаблона пересобирает оформление из сохранённой ревизии, не
  обращаясь к модели повторно;
- `ml_service` не хранит состояние запросов — масштабируется копиями за
  балансировщиком; каждая копия строит одинаковый in-memory RAG-индекс из
  read-only справочников образа.

Куда подключаются внешние системы:

| Что | Точка подключения |
|---|---|
| Корпоративный справочник сотрудников | `requisites_validator`: источник значений вместо `missing` |
| СЭД | новый адаптер рядом с `docx_renderer`: отдать файл не в браузер, а в систему |
| Другой провайдер ИИ | `ml_service/llm/ollama.py`, HTTP-контракт не меняется |
| Корпоративные шаблоны | `POST /api/templates/upload` либо папка в `assets/` |

Микросервисы, отдельный кластер и нагрузочный стенд заданием не
требуются и не делались.
